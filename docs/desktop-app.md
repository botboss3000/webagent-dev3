# Desktop and Android app

The installable app is a Tauri window (`crates/app-shell`) around the normal WebAgent
server, which it starts as a companion process. The server binary is the same
`webagent-v3` built with the core tier: `--no-default-features --features
linked-context,stable-abilities` (no local tool worker, no Administrator pack, ability
plugins linked in).

## How it runs

1. The shell unpacks its bundled app files into the user's app-data folder
   (`%APPDATA%\live.webagent.app`, `~/.local/share/live.webagent.app`, the Android app's
   data folder): `app/` (UI, abilities, configuration, gate and engine descriptors) is
   replaced whenever the bundle changes; `checkout/` (the live settings files from
   `live-files.json`) is only filled in where files are missing, so settings changed in
   the app survive upgrades.
2. It starts the server with `V3_PROCESS_ROLE=desktop` on a free `127.0.0.1` port.
   Desktop mode runs the API and the agent loop in one process, creates the run-control
   files itself, and saves live settings files directly into `checkout/` (no broker).
   The data roots come from `V3_STATE_ROOT`, `V3_RUNTIME_ROOT`, `V3_WORKSPACE_ROOT`,
   `V3_APP_ROOT`, `V3_ABILITIES_ROOT` and `V3_CHECKOUT_ROOT`; `V3_SECURE_COOKIE=false`
   because the page is plain HTTP on loopback.
3. The window shows a loading page until `/health/ready` answers, then opens `/app`.
   First start shows the usual admin setup page.
4. Closing the app closes the server's standard input (`V3_STOP_ON_STDIN_EOF=1`); the
   server drains its runs and stops, and is killed after 20 seconds.

The server runs beside the app executable on desktops (Tauri `externalBin`) and from
the APK's native-library folder on Android (`libwebagent_server.so`), the one app
folder Android allows executing from; the APK keeps native libraries extracted for
this, and allows plain HTTP to loopback only.

## What the core build leaves out

Linux-server parts stay Linux-only and report themselves unavailable elsewhere: the
local tool worker (file, shell, terminal, Git, browser tools), the Administrator pack
and its pages (Builds, Host Admin), engine components and automation reducers (they
need the Linux sandbox), and the MCP, Diagnostics and optimization plugin processes.

## Building

```sh
python3 crates/app-shell/package.py linux     # .deb, .rpm, AppImage
python3 crates/app-shell/package.py windows   # NSIS installer, cross-built with MinGW
python3 crates/app-shell/package.py android   # APK for arm64 phones and x86_64 emulators
python3 crates/app-shell/package.py macos     # .app/.dmg, on a Mac
```

Prerequisites per platform are listed at the top of `package.py`. The Tauri project
is outside the server workspace (its own `Cargo.lock`), so server releases never build
it. Icons are generated from `ui/app-icon.svg` on each build, and the Android project
(`gen/android`) is generated by `cargo tauri android init` and adjusted by
`package.py`; neither is committed.
