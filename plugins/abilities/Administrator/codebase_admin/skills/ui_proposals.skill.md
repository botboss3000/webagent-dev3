# UI proposals with screenshots

Show the user each option rendered in the real app, let them choose, and release only the chosen one.

Work only from this request and the live source. Do not read other sessions or reuse their variants, screenshots or notes unless the user asks.

Do not open a broker task or edit source until the user has chosen. Options are front-end only: if an option needs data the backend does not provide yet, derive or mock it in the variant's JavaScript and say so in its description. Screenshots come only from Browser Control; the shell has no usable browser. Write each variant's files with one batch of file_write calls.
The preview link below is ready to use: do not read its implementation. The app's design tokens (`--bg-*`, `--fg-*`, `--font-*`, colours) are defined in `/code/build-service/shared-ui/ui/shared/css/design-system.css`, served at `/ui/shared/css/design-system.css`; `/code/ui` only uses them.

1. Read the files to change from `/code/ui` once, in one batch, and decide the options. Before starting sub-agents, save the capture as a session script with `script_save`, following the session scripts skill: params for the preview link, the conversation to open and the label prefix, and a desktop and a phone screenshot of the changed element. Then, with two or more options, your next step is one `start_spawn` call per option, all in that one step (Agent Management; see the subagents skill). Do not write variant files in this session yourself. Give each its option's design, the source paths, steps 2–3 below for its own session, and its exact screenshot labels: `<Option letter> · <name> · desktop` and `<Option letter> · <name> · phone` (for example `A · Step rail · desktop`). Tell it to take its final screenshots with `script_run` on that script, giving the exact args (its full preview link, its OWN session's sample view `/app?session_id=<its session id>&ui_sample=activity`, and `<Option letter> · <name>` as the label prefix). It writes into its own workspace (`/workspaces/<its session id>/previews/<variant>/ui/…`). Tell each sub-agent to end with this fixed final reply and nothing else: the option name, a one-line summary, its full preview link, and both labelled screenshots from the capture script (desktop and phone) attached to that same reply; if either is missing, it runs the script again before replying. End your turn until they report, then do step 4 with all their results.
2. For each option, write only the changed files into the session's workspace, `/workspaces/<session id>/previews/<variant>/ui/`, keeping their path below `ui/` (for example `previews/option-a/ui/chat/elements/activity-group/style.css`). Variant names use lowercase letters, digits, `-` and `_`. Unchanged files come from the live UI automatically. Pass only `path` and `content` to `file_write`; workspace writes refuse `mode`, `delete` and the broker task fields, which belong to broker task files. Workspace writes release nothing.
3. Capture each variant with one Browser Control `browser_input` `script` call: navigate to `/api/v3/sessions/<this session id>/ui-preview/<variant>`, navigate to the page to show, read and click what must be opened, `wait_for` it, then a step with `"screenshot": true` and a `label` naming the option and view (for example `Option A · step rail · phone`); add a `viewport` `phone` step, navigate again and screenshot for the phone view. Equivalent detail: in Browser Control, open `/api/v3/sessions/<this session id>/ui-preview/<variant>` on the WebAgent app. It sets a private one-hour preview for that browser only and opens `/app`. Navigate to the page the change affects, then take phone (390 px) and desktop screenshots. Repeat for each variant; `/api/v3/sessions/<id>/ui-preview/off` ends the preview.
   For chat activity changes, capture the fixed sample instead of the live conversation: `/app?session_id=<this session id>&ui_sample=activity` shows one static activity group (several model steps with tool calls, one of them failed) after the conversation's first message, and none of the session's own groups, so captures do not change while the run works. Open it with a click on `.v2-activity-group > summary` after a `wait_for` visible step.
   Check a render with one `script` call that combines its read, measure and wait steps (plus a screenshot step if needed), not one browser call per check. Take the final screenshots with the parent's capture script (`script_run`). A session's browser can open only its own conversation, so never pass the parent's conversation to a sub-agent.
   Capture each option once at each width. Fix only what is broken in a capture (missing, overlapping or cut-off content) and capture it again; leave visual polish for after the user chooses.
4. Present the sub-agents' final replies directly: their screenshots, one-line summaries and full preview links (`https://<app origin>/api/v3/sessions/<this session id>/ui-preview/<variant>`, plus the `…/ui-preview/off` link once), so the user can open and try each option in their own signed-in browser. Do not call read_session to collect screenshots, do not capture them again, and do not render-check your own reply. Present each sub-agent's own preview link and screenshots as reported: do not copy variants into your workspace, re-capture or edit them. If a variant needs a fix, send it back to the sub-agent that owns it with `message_session`. Offer the choice with one `present_chat_component` `choice` panel titled after the topic (for example "Activity grouping options"; a click sends "<title>: <option>"), and, so the user can combine options, a `form` panel with a `multi` field listing the same options. Do not release anything before the user chooses.
5. Apply only the chosen variant's files to source with the task file tools (one broker task), then finish it. Mention the other variants are left unreleased in the workspace.

Preview files are served only to the signed-in owner of the session and never cached. `/ui/` shared assets and the API are not overlaid, so changes there cannot be previewed this way.

Progress updates: one sentence, only at phase changes (spawning, presenting, releasing).
